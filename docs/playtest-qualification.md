## Promise and boundary

The implemented player-facing core is **physical spirit acquisition and finite, themed commerce**: player-credited eligible mob deaths release Malum-mapped spirits at the victim, seven ordinary aspects convert to commerce currency, and themed wandering traders / villagers sell authored goods for spirits with stock limits. Ordinary visits, additional Spirit Fair visits, camp posts/campfires and local market browsing have production code. Resident needs, gathering, settlement generation, barter and Player Stalls were extracted to the private, non-compiling `better-content/better-villager-society` source snapshot and are not part of this mod's current source. `BetterSpiritCommerce` registers the remaining event handlers, networks, commands and five explicit GameTest classes; the common config and `data/better_spirit_commerce/spiritcommerce/{spirit_economy_policy,wandering_pool}.json` control policy and catalogue. See [spirit-acquisition.md](spirit-acquisition.md) for the **current checkout's** exact Malum conversion, exclusions, immediate release, Tempo limitation and queued-credit migration/rollback warning. That page is not an assertion about build-69 bytes: compare the packaged JAR first. Tempo remains registered in recipes/trades, but ordinary Malum mobs supply no Tempo via this death route; check whether required playtest progression depends on it before declaring the economy playable.

Do not turn the [pack design's historical society ambition](../../../better-content-modpack/docs/design.md#spirit-commerce-and-emergent-society) into a shipped claim. Resident barter and Player Stalls are absent from this source candidate, and the [asynchronous player-trade proposal](../../../better-content-modpack/docs/design.md#a-custom-asynchronous-player-trade-system) remains unimplemented. The proposed stand-alone trading UI / broader UX redesign is likewise deferred, not part of this source qualification. The current Local Market is nearby merchant discovery/selection, not an asynchronous market (`LocalMarket.java`).

## Task, dependency and CI contract

`gradle.properties` pins Minecraft **1.20.1**, Forge **47.4.13**, Java **17**, Commerce **1.0.1** (with specific Create/Ponder/Flywheel/Registrate pins). `verifyFast` depends on Gradle `check` (JUnit `test`, Jacoco report, Python native-diagnostics unit checks) and `verifyLocalProviderRouting`; `verifyFull` additionally requires `headlessGameTest` and `verifyNativeRunFixture`. `stageRuntimeJar` stages the reobfuscated JAR and checks its production refmap and absence of native-fixture additions; `assemble` depends on staging. The native-only source set takes exact authored Malum advancement/crushing fixes from the sibling pack, a generated refmap and a fresh nonce / properties fixture, **not** production content. Native diagnostics are strictly scoped to this Forge dev fixture, not the pack-wide warning/performance policy. `runVisualServer` and `runVisualClient` are separate visual profiles; the `verify*VisualHarness` tasks only inspect already produced files.

Gradle configuration requires local private provider JARs **even if the celestial runtime is absent**: `better-celestial-events-0.1.0.jar` (compile-only by default, runtime opt-in `-PcelestialRuntime=true`), `better-dimension-fonts-1.0.0.jar` (compile + native runtime), `better-compat-fixes-0.1.9.jar` and `better-gameplay-notices-1.0.1.jar` (native runtime). The default locations are sibling `build/libs/` directories; `BC_CUSTOM_MOD_JAR_DIR` must be nonblank if specified and supplies all four. Private coordinates route only to local Ivy, not public Maven; `verifyLocalProviderRouting` tests that rule. Native Malum/Lodestone/Curios, JEED, JEI, Rats/Citadel and other pinned CurseMaven dependencies still need the resolved toolchain. The CI workflow requires `BC_CI_PACK_REF` as an immutable 40-character reviewed pack commit, checks out that pack for `prepare-native-ci-inputs.py`, uses Python 3.11 / Temurin 17, runs `./gradlew --no-daemon --max-workers=2 --no-build-cache verifyFull stageRuntimeJar` and retains reports/logs/provider receipts for 14 days. A configured workflow is not a passed CI result. Running any repository test requires explicit human authorization unless a standing approval clearly covers that exact run; none was used here.
